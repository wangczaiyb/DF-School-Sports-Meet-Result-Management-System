# 原型评审与实现说明

## 保留的视觉语言

三个参考页面中，`运动会.html` 与 `运动会个人.html` 的 SHA-256 完全相同。新系统合并为一个成绩业务入口，没有重复开发两个相同页面。

保留并提升了以下视觉特征：

- 蓝白主色、浅灰页面底色和白色卡片。
- 绿色突出积分、正常状态和已发布状态。
- 蓝色表头、固定信息层级、成绩表格和前三名金银铜强调。
- 学院总分排名、个人成绩表、项目筛选和导出入口。
- 登录页增加抽象跑道、身份选项、品牌区、加载、密码显隐和 Caps Lock 提示。

## 已修复的原型逻辑

| 原型问题 | 新系统处理 |
|---|---|
| 使用 `localStorage` 保存正式数据 | 全部账号、赛事、权限、赛程、成绩、审核和导出记录写入 SQL 数据库 |
| 以姓名作为运动员唯一标识 | 使用数据库 ID 和唯一学号 |
| 男子、女子、学生、教工、阶段混合排名 | 项目保存组别、人员组、项目类型和阶段；按项目/轮次独立排名 |
| 根据名称含“接力”判断项目类型 | 使用 `INDIVIDUAL`、`RELAY`、`TEAM` 明确字段 |
| 同学院积分被最后一名运动员覆盖 | 已发布结果逐条累加并按金银铜数处理同分 |
| 删除单条成绩清空整个学院项目积分 | 团体分由已发布成绩实时汇总，不保存可手工覆盖的学院总分 |
| 前端直接计算排名和积分 | 排名、并列积分、权限、审核和发布均由后端执行 |
| 未审核数据可能被前端读取 | 公共接口只查询存在 `published_at` 的发布快照 |
| CSV 代替正式送审文件 | 后端使用 openpyxl 输出带审核人员、打印区和 A4 横向设置的 `.xlsx` |

## 数据保存位置

- Python SQLite 正式数据库：`data/sports_meet.db`
- 成绩单：`data/exports`
- 备份：`data/backups`

前端 `localStorage` 只保存当前登录令牌和最小用户会话信息，不保存赛事业务数据。
